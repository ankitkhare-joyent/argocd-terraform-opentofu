# Lab 07 · Day 2: drift, rotation, rollback

One sitting, about 35 minutes. Background: [docs/08](../docs/08-day-2-operations.md).

After this lab you can explain:

- what self-heal reverts, and what it deliberately leaves alone
- how long a rotated password takes to reach a pod, and why env vars lag behind files
- why rollback in GitOps is `git revert`, and what users see while a bad version rolls out

## 1. Drift

**Predict (P1):** someone scales prod to 5 replicas by hand. What happens, and how fast?

```bash
start=$(date +%s); kubectl -n demo-prod scale deploy demo --replicas=5
until [ "$(kubectl -n demo-prod get deploy demo -o jsonpath='{.spec.replicas}')" = 2 ]; do sleep 1; done
echo "back to 2 after $(( $(date +%s)-start ))s"
```

**Predict (P2):** now they add a label `hotfix=true` to the same Deployment. Reverted too?

```bash
kubectl -n demo-prod label deploy demo hotfix=true; sleep 20
kubectl -n demo-prod get deploy demo -o jsonpath='{.metadata.labels.hotfix}{"\n"}'
argocd app get demo-prod -o json | jq -c '{sync: .status.sync.status}'
kubectl -n demo-prod label deploy demo hotfix-        # tidy up
```

## 2. Rotation

**Predict (P3):** you rotate the dev password and username in OpenBao and force External Secrets to refresh. How
long until the *file* in the pod changes? Does the `DB_USERNAME` env var change?

```bash
bao kv metadata get -format=json secret/apps/demo/dev | jq -c '{current: .data.current_version, versions: (.data.versions|keys)}'
OLD_FILE=$(kubectl -n demo-dev exec deploy/demo -- cat /etc/demo-db/password)
bao kv patch secret/apps/demo/dev password="$(openssl rand -hex 12)" username=demo_dev_app_v2 > /dev/null
start=$(date +%s)
kubectl -n demo-dev annotate externalsecret demo-db force-sync=$(date +%s) --overwrite
until [ "$(kubectl -n demo-dev exec deploy/demo -- cat /etc/demo-db/password)" != "$OLD_FILE" ]; do sleep 2; done
echo "file updated in pod after $(( $(date +%s)-start ))s"; unset OLD_FILE
echo "env: $(kubectl -n demo-dev exec deploy/demo -- sh -c 'echo $DB_USERNAME')"
echo "file: $(kubectl -n demo-dev exec deploy/demo -- cat /etc/demo-db/username)"
```

Make the env var catch up:

```bash
kubectl -n demo-dev rollout restart deploy/demo && kubectl -n demo-dev rollout status deploy/demo
echo "env after restart: $(kubectl -n demo-dev exec deploy/demo -- sh -c 'echo $DB_USERNAME')"
bao kv metadata get -format=json secret/apps/demo/dev | jq -c '{current: .data.current_version}'
```

## Break it, then fix it: a bad release

**Predict (P4):** you push a dev image tag that doesn't exist. Do users of dev lose service? What do sync and
health say?

```bash
sed -i '' 's/newTag: "6.15.0"/newTag: "does-not-exist"/' gitops/apps/demo/overlays/dev/kustomization.yaml
git commit -qam "lab07: bad image tag" && make push
argocd app get demo-dev --refresh > /dev/null; sleep 30
argocd app get demo-dev -o json | jq -c '{sync: .status.sync.status, health: .status.health.status}'
kubectl -n demo-dev get pods
```

**Predict (P5):** roll back with `git revert`. How long until dev is healthy, and what happens to the broken pod?

```bash
start=$(date +%s); git revert --no-edit HEAD && make push
argocd app get demo-dev --refresh > /dev/null
wait_app demo-dev; echo "recovered $(( $(date +%s)-start ))s after the revert"
kubectl -n demo-dev get pods
```

## Wrapping up the lab track

Your local `main` now has the lab commits, and so does Gitea. To return to a clean copy of the repo:

```bash
git fetch origin && git reset --hard origin/main      # local copy = GitHub
git push -f gitea main:main                           # Gitea (what Argo CD reads) = GitHub too
make down                                              # or: make stop, to keep the stack for later
```

## Check your predictions

**P1.** Back to 2 after 4 seconds. Argo CD watches the cluster, sees `replicas: 5` differ from Git, and
`selfHeal: true` re-applies Git. A manual scale doesn't survive.

**P2.** Not reverted. The label is still there (`true`) and the app stays `Synced`. Argo CD compares the fields
*Git declares*. A label Git never mentions isn't drift to it. Self-heal enforces your manifests; it doesn't wipe
everything else.

**P3.** Before: `{"current":1,"versions":["1"]}`. The file changed 67 seconds after the patch. ESO updated the
Secret almost immediately (forced refresh), and the kubelet then refreshes mounted Secrets on its own sync period (up
to about a minute). The env var did **not** change (`demo_dev_app`, while the file says `demo_dev_app_v2`). Env vars
are copied once at container start. After `rollout restart`: `env after restart: demo_dev_app_v2`. OpenBao keeps
version history: `current` is now 2. To roll back the secret, read or restore version 1 with
`bao kv rollback -version=1 secret/apps/demo/dev`.

**P4.** No loss of service. The app is `Synced` (Git was applied) but `Progressing`, and it turns `Degraded`
once the Deployment's progress deadline (10 minutes) passes. The pods:

```
demo-5c6f575b4b-6rqvv  1/1  Running
demo-848645875f-9zzqg  0/1  ImagePullBackOff
```

A rolling update never removes the old pod until the new one is ready, so the old version keeps serving.

**P5.** `Synced/Healthy` 10 seconds after the revert push. The broken ReplicaSet is scaled to zero, and only the
original pod remains. The bad commit and its revert both stay in history, so the audit trail shows what happened.

## What to remember

- Self-heal reverts fields Git declares, quickly. It doesn't own fields Git never mentions.
- Rotations reach mounted files in about a minute without restarts. Env vars need a restart (or Reloader).
- Rollback = `git revert` + push. Rolling updates keep the old version serving while you do it.
